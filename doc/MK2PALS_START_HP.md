# Retail's mirror-match costumes, on Start+HP

**What changed:** holding **Start + High Punch** at the character select screen
now gives each of Midway's twelve fighters the costume he wore in a **retail
mirror match** — `character_palettes_2` as the read-only tree holds it — and
the bloodied palette his cut-up art is actually drawn in.

The palettes live in `data/MK2PALS.IMG` (openable in IMGTOOL, with a reference
sprite beside each one) and `src/MK2PALS.ASM` (what the ROM links). Both are
generated by `tools/make_mk2pals.py`; Phase D fails the build if they drift.

## Why the words come from `mk2-readonly` and not from `src/`

Two of the twenty four have **drifted in this tree** and are not what retail
shipped, so reading the local symbol would have put something else in the slot
under a retail label:

| symbol | entries differing from retail |
|---|---|
| `KATBLU3_P` | 28 of 64 |
| `RADRED_P` | 2 of 64 (re-extracted here from `RADBOLT1.IMG`) |

Kitana is the instructive one. Retail's `KATBLU3_P` is `KAT11.IMG:KATBLU3_P`;
*this* tree's symbol of the same name is `KAT1.IMG:KATBLU2_P`. Same name, two
different palettes — which is why the generator matches **by content**, never
by name, and prints the record each palette was found in. `--report` shows both
the provenance and the drift.

The source of truth is the read-only tree's `src/`, not its IMG libraries: the
ASM is the copy retail's ROM shipped, and the libraries are the authoring side,
which can disagree with it.

## Why they are copies and not the shipped symbols

Pointing slot 4 at `tmgold_p` would make Start+HP an **alias** of Start+LP:
repainting the costume in IMGTOOL would silently move the mirror match with it.
The twelve are their own records under their own names, so Start+HP can be
repainted on its own.

Cost: **3,302 bytes** of program ROM (headroom 93,140 → 89,838).

## What this displaced

Slot 4 already held a costume for every fighter. Ten of those are no longer on
any Start+button lane:

`TMBLACK_P`, `LIUALT2_P`, `JCALT1_P`, `UGALTHP_P`, `KITALT2_P`, `MILALT2_P`,
`TMOVIE_P`, `RADALT_P`, `REP_P`, `SCORP_P`

`SUB_P` survives — it is also `character_palettes_7[8]` (Start+Coin). The
palettes themselves are still defined and linked; nothing on the select wheel
reaches them.

Three rows are now **the same colours as Start+LK**: Sub-Zero, Reptile and
Scorpion, because `character_palettes_6` rows 8-10 are already `SUB2_P`,
`REP3_P` and `SCORP2_P` — the same retail palettes this slot now carries as
copies. Eight more duplicate **Start+LP**, for the eight fighters whose
`character_palettes_2` this tree never changed.

If that is not wanted, the fix is a swap rather than a revert: move each
displaced costume into the lane its retail alternate vacated.

## The library

`data/MK2PALS.IMG` is in **no LOD**. LOAD2 never reads it and not one pixel of
it reaches a ROM — only `src/MK2PALS.ASM` is linked. It is a reference and
authoring library, the same role `data/KATPAL.IMG` plays.

It carries 24 palettes and 24 frames to judge them against, because a palette
on its own cannot be judged:

* `M2<xx>STANCE` — the fighter's stance, under his Start+HP costume
* `M2<xx>TORSO` — his torso rip, under the bloodied palette

Pixels are copied verbatim out of the read-only gore library that already
carries both of that fighter's palettes (`HATHED11`, `KANG10`, `CAGE10`,
`UGMO10`, `KAT11`, `TSUNG10`, `RAID9`, `NINJAS11`, `NUJAX10`). Kitana/Mileena
share a body and so do the three ninjas, so those records hold identical pixels
and differ only in `palnum` — which is the point: it is what lets IMGTOOL show
the costumes side by side.

Baraka's rip was authored as two strips with no composite, so his reference is
`UGRIPTORSO1A`.

**`palnum` is offset by three.** The library header counts `NUMDEFPAL` phantom
palettes that are not in the file, so `palnum = 3 + index in the file`.

## Editing a costume

Edit `data/MK2PALS.IMG` in IMGTOOL, then:

```
python tools/make_mk2pals.py --apply     # re-emit src/MK2PALS.ASM
python build.py --asm-only && python makerom.py && python mamerom.py --source-video
```

`--asm-only` is enough: the IMG is in no LOD, so there is nothing for LOAD2 to
repack and the video ROMs do not move.

**Nothing else would notice a repaint.** Nothing in the build promotes an IMG
palette into the ROM, so an edit that was never re-imported changes no ROM byte
and produces no error. That is the whole reason Phase D runs
`make_mk2pals.py --check`.

## The four edits a costume row needs

Repointing a row is never one edit. All four are done here:

1. `character_palettes_4` (MKGUYS.ASM)
2. `bloody_character_palettes_4` — `change_to_bloody_pal` tests
   `b_repalt2_pal` and branches to table 4
3. `death_fade_excludes` — a fighter never dims in his own costume, and this
   list is matched **by symbol**, so Midway's words under a new name are not
   exempt. `tools/audit_fade_excludes.py --check` (Phase D) catches an omission
4. the `.ref` block at the top of MKGUYS.ASM

## Proof

`tools/run_mk2pals_test.ps1` — **12/12 PASS**, negative control **12/12 FAIL**.

It drives the **real gesture**, not the table: 1P Start held across P1 High
Punch at the select screen, which is what `psr_p1_masks` (MKSEL.ASM) claims the
lane on. Poking `@alt_pal_owner` would prove the table is wired and nothing
about whether a player can reach it. Start+HP is both the claim and the
confirm, so the two are one press.

It then reads the **colour RAM the fighter's object is pointing at**, in the
fight, and compares all 63 transferable entries with the words in
`data/MK2PALS.IMG`. The expectation is regenerated from the IMG before every
run (`tools/mk2pals_expect.py` → `tools/mk2pals_expect.lua`), so a pass means
"the screen matches the art", not "the screen matches a number in a rig".

```
powershell -File tools/run_mk2pals_test.ps1                  # all twelve
powershell -File tools/run_mk2pals_test.ps1 -Char kitana
powershell -File tools/run_mk2pals_test.ps1 -Negative        # must FAIL
```

**The lane is checked before the colours.** A colour mismatch when the gesture
missed is a rig problem, not a wiring problem, and the two look identical in a
bare diff — so the rig fails on `oflags2` having no `b_repalt2_pal` first, and
says so in those words.

`-Negative` asks for the palette slot 4 held *before* this change. Every trial
must fail; a pass would mean the rig is not reading the colour RAM at all. Note
that the naive control — comparing against Start+LP — **cannot discriminate**
for eight of the twelve, because those rows are now the same palette. The rig
refuses a trial whose two expectations are identical rather than passing it.

P2 is always somebody else (Jax, or Liu Kang when P1 is Jax) so no trial is a
mirror match, which would send P2 down a different lane.

### What is proven where

* **On screen, all twelve:** the clean Start+HP costume, 63/63 exact.
* **In the linked ROM:** all 24 palettes, word for word against the read-only
  tree, read back out of `rom/mk2_flat.bin` at the addresses `src/mk2.map`
  gives — plus both slot-4 tables pointing at them. `bloody_character_palettes_4`
  is a local symbol the linker strips, so it is located by its content: the run
  of twelve pointers occurs exactly once in the ROM.
* **By construction:** the bloodied half is reachable, because
  `change_to_bloody_pal` branches on `b_repalt2_pal` — the same flag the rig
  measured as set on the fighter. It has not been watched on screen through an
  actual fatality.
